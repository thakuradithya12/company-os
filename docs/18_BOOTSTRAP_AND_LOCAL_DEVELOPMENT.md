# 18 — Repository Bootstrap and Local Development

## Status

Phase 2 — repository bootstrap and engineering foundation. The founder approved the eight logical roles on 2026-10-21. This phase provides only the application shell, configuration validation, database migration baseline, health checks, CI, and repeatable setup. It does not implement any agent behavior.

## Supported baseline

- Windows 11 with PowerShell 7 or Windows PowerShell 5.1 for the setup script.
- Python 3.13.16, managed by `uv`.
- Node.js 24 LTS for the web project.
- PostgreSQL 17 for local integration/development.
- Docker Desktop with Docker Compose v2 is the full-stack convenience path. The API tests themselves can run without Docker by using an in-memory SQLite database for readiness checks.

Python 3.13 is selected over a newly released major version to favor the established compatibility surface for application dependencies. Node 24 is the active LTS line as the bootstrap work is being prepared. Versions and package manager lock behavior must be re-reviewed during planned dependency updates, not silently changed during feature development.

## First setup on Windows

1. Install Git for Windows, Node.js 24 LTS, and `uv` using their official installers. Open a new PowerShell window after installation.
2. From the repository root, run:

   ```powershell
   Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
   .\scripts\bootstrap.ps1
   ```

3. The script validates Node 24, installs Python 3.13.16 through `uv`, generates `uv.lock` and `apps/web/package-lock.json`, installs exactly the locked environments, copies `.env.example` to `.env` if necessary, checks environment configuration, runs Python lint/tests, then checks and builds the Next.js app.
4. Inspect the generated lockfiles and test output. Do not push until the entire script succeeds. If a check fails, fix the first failure, rerun the script, and do not proceed to agent implementation.
5. Optionally validate PostgreSQL migration execution on a machine with Docker Desktop running:

   ```powershell
   .\scripts\bootstrap.ps1 -WithDockerDatabase
   ```

6. Rerun the locked checks at any later time with:

   ```powershell
   .\scripts\check.ps1
   ```

The lockfiles intentionally must be generated by the package managers on a networked developer machine. Use uv 0.13.4 or newer to provision the pinned Python patch version. Do not hand-author either lockfile. The project CI requires both files to exist and be in sync before a change is accepted.

## Local full-stack run

Once `uv.lock` and `apps/web/package-lock.json` are present and the bootstrap checks pass:

```powershell
docker compose up --build
```

Open the web shell at <http://localhost:3000>. API liveness is at <http://localhost:8000/health/live>; database-backed readiness is at <http://localhost:8000/health/ready>.

Compose binds the web, API, and PostgreSQL ports to loopback only. PostgreSQL is exposed on host port `55432` by default while remaining on port `5432` inside the Compose network, to avoid colliding with an existing host PostgreSQL service. The default Postgres credentials are for local development only. Never expose this stack publicly or reuse these credentials in staging/production.

To stop services without deleting the database volume:

```powershell
docker compose down
```

`docker compose down -v` deletes the local PostgreSQL volume and should be used only when you intentionally want to destroy its contents.

## Environment contract

| Variable | Purpose | Rule |
|---|---|---|
| `COMPANY_OS_ENVIRONMENT` | `development`, `test`, `staging`, or `production` | Default is development; explicit in CI/Compose |
| `COMPANY_OS_LOG_LEVEL` | Application log level | Must be one of DEBUG, INFO, WARNING, ERROR |
| `COMPANY_OS_DATABASE_URL` | SQLAlchemy database URL | Required for full readiness; PostgreSQL uses `postgresql+psycopg://...` |
| `COMPANY_OS_APP_SECRET_KEY` | Reserved application secret for future signed/session capabilities | Required outside development/test and at least 32 characters; never print or commit it |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | Local Compose database setup | Development-only values in `.env.example` |
| `COMPANY_OS_POSTGRES_HOST_PORT` | Host port for local Compose PostgreSQL | Defaults to `55432` to avoid conflicting with a PostgreSQL service already using `5432`; Compose still uses port `5432` internally |

The API can start with no database URL so process liveness remains separately observable, but readiness returns HTTP 503 until a database is configured and reachable. `python -m company_os.config_check` validates whether full-stack configuration is present without printing secret values.

## API foundation

- `GET /health/live` returns 200 when the process responds. It does not promise the database is available.
- `GET /health/ready` runs `SELECT 1` against the configured database. It returns 200 only when the database check passes; otherwise, it returns 503 with a non-sensitive check status.
- The initial Alembic revision intentionally introduces no domain tables. It proves the migration pipeline exists without prematurely deciding task/agent/CRM/memory schemas. Domain migrations belong to their approved platform work packages.

## Native command failure handling

The PowerShell scripts explicitly check the exit code of every native tool they invoke (`uv`, `npm`, `docker`, and related commands). This is required because a failed native executable is not consistently treated as a terminating PowerShell error across Windows PowerShell 5.1 and PowerShell 7 configurations. The bootstrap must stop immediately on a non-zero exit code and must never print the success message after a failed command.

When `-WithDockerDatabase` is used, the script first verifies that the Docker Engine is reachable, then starts the Compose database and waits for its readiness check before invoking Alembic. If Docker cannot start the database, migration is not attempted against an unrelated PostgreSQL server listening on the host's port 5432.

## Validation status and limitations

The founder's Windows run confirmed that Python dependency resolution, lockfile generation, seven backend tests, frontend type checking, and the Next.js production build passed. The optional PostgreSQL migration gate did not pass because Docker Desktop's Linux engine was unavailable; the old script then attempted to connect to a different PostgreSQL service on localhost and received a password-authentication error. That run must be treated as failed. The native exit-code checks, Docker preflight, database readiness wait, and default host-port mapping above correct the false-positive success behavior and reduce the risk of contacting an unrelated local PostgreSQL service. Re-run the complete bootstrap, Docker migration, Compose startup, and GitHub Actions checks before declaring Phase 2 accepted.
